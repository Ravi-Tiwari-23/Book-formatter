# Production Text Integrity Design

## Purpose

Protect the approved source-derived wording throughout production without blocking valid typography or exposing Python tracebacks to normal users. The expected production text is the user-approved result of source OCR and review. Raw OCR and the reference PDF are evidence used before approval; neither is the production baseline.

## Confirmed Root Cause

The current verifier normalizes whitespace, concatenates text extracted from every final-PDF page, and requires each approved paragraph to occur as an exact substring. The current production artifact reports 11 missing paragraphs even though all 11 are present:

- Nine paragraphs cross page boundaries where generated page numbers are inserted into extracted text, such as `intelligence and 7 wisdom`.
- Two paragraphs contain renderer line-wrap hyphen artifacts, such as `north-east` becoming `north- east`.

The failure is raised as a generic `ValueError`. The Streamlit build handler catches only `BuildBlockedError`, so the generic exception becomes a visible traceback instead of a reviewable QA result.

The persistent build cache is not the source of this incident because its key includes hashes of approved text and structure data. A separate stale-state risk exists: changing a correction invalidates finalization and generated artifacts but does not invalidate `project.structure_override`, allowing renderer blocks to retain wording from an earlier approval state.

## Canonical Text Model

Production integrity is based on ordered canonical units:

`Book -> Chapter/section -> Paragraph or list item`

Each unit records:

- a stable canonical ID derived from the correction ID and section context;
- chapter number and title;
- unit type and order;
- original approved text;
- semantic normalized text;
- a SHA-256 hash of normalized text.

Canonical units are built only from approved source corrections and source-section fallback content where the existing pipeline already permits that fallback. Reference text is never promoted into the canonical model except through an explicit approved correction decision.

## Normalization

Semantic comparison applies Unicode NFC normalization and removes differences introduced solely by presentation:

- repeated whitespace, line endings, paragraph wrapping, and non-breaking spaces;
- soft hyphens and zero-width characters;
- smart/straight quote variants where they are semantically interchangeable;
- page-break artifacts;
- a hyphen followed by layout whitespace when it represents the same approved hyphenated word.

Normalization does not case-fold words, alter punctuation generally, correct spelling, summarize, or otherwise rewrite body content. Hindi, English, and mixed-script text use the same Unicode-safe path.

## Renderer Synchronization

Before rendering, the pipeline compares canonical units with the source-derived units in renderer blocks. Decorative/generated blocks are classified separately and excluded from this comparison:

- title-page duplication;
- TOC labels and page numbers;
- page numbers;
- running headers and footers;
- chapter numbering labels such as `REMEDY 01`;
- decorative dividers, watermarks, image captions generated by the formatter, and PDF metadata.

If renderer input differs because an override is stale, the pipeline regenerates the renderer blocks from current canonical units and reruns the pre-render check. The automatic repair is recorded in the QA report. A renderer-only text edit is never silently accepted. If it cannot be mapped safely, production stops with structured issues.

Structure editing remains available for block type, hierarchy, and layout. Wording changes must be adopted explicitly into canonical approved text through the review action rather than existing only in renderer state.

## Two Integrity Gates

### Pre-render gate

The authoritative gate compares canonical approved units with the exact source-derived units sent to the renderer. It detects:

- `MISSING`: canonical unit absent from renderer input;
- `DUPLICATED`: canonical unit occurs more than once;
- `UNEXPECTED`: source-derived renderer unit has no canonical counterpart;
- `MODIFIED`: mapped unit has different semantic text;
- `ORDER_CHANGED`: canonical units occur in a different sequence.

### Post-render gate

The post-render gate ensures the PDF did not drop or mutate renderer input. PDF extraction is page-aware and removes known generated furniture before comparison. Page-number tokens are removed only when identified as page furniture, not merely because a body paragraph contains a number. TOC and protected/decorative pages are excluded using render metadata and known page ranges. Line-wrap hyphenation is normalized semantically.

The post-render gate uses ordered unit alignment rather than one whole-book substring search. It protects against actual rendering loss while allowing typography-only differences.

## Reports and Error Contract

The verifier returns a serializable report containing:

- overall status and stage (`PRE_RENDER` or `POST_RENDER`);
- counts for chapters and verified units;
- resynchronization status;
- ordered issues;
- for every issue: canonical ID, chapter, unit order, difference type, expected and actual text, normalized lengths, SHA-256 hashes, and a concise difference excerpt;
- summary counts for missing, duplicate, unexpected, modified, and reordered content.

The report is written before a production failure is raised. Production failures use `ProductionIntegrityError`, which carries the complete report and report path. Developer logs retain traceback and structured hash/length details, while user-facing output omits sensitive filesystem paths.

## Streamlit Experience

Before a successful final build, the UI shows a text-integrity summary such as:

- chapters checked;
- paragraphs/list items verified;
- no approved text missing;
- no duplicates or unexpected text.

On failure it shows `FINAL BUILD BLOCKED`, the number of issues, compact chapter-level issue rows, and controls to review issues and download the JSON QA report. It does not display a raw Python traceback.

Each expanded issue shows approved text, renderer text, and a concise highlighted difference. Supported actions are:

- **Use Approved Text** (recommended): restore renderer input from canonical text;
- **Keep Current Renderer Text**: explicitly adopt renderer wording into the corresponding canonical correction, then require finalization again;
- **Edit**: update the canonical correction through explicit review and require finalization again;
- **Mark Resolved**: available only after the compared values pass or an explicit adoption/edit has made them canonical.

Any action that changes canonical wording clears `text_finalized`, generated artifacts, the relevant structure override, and integrity-review state.

## State and Cache Rules

- Correction changes invalidate `structure_override` as well as finalization and artifacts.
- The finalized state stores the approved-text hash, not only a boolean. A build is enabled only when the current approved hash matches the finalized hash.
- Build-cache entries continue to include approved and renderer-structure hashes.
- Integrity-report state is keyed by those same content hashes so an old report cannot be shown for new wording.
- Automatic renderer resynchronization happens before cache lookup or produces a new renderer hash.

## Files and Responsibilities

- `src/truelogger/integrity.py`: canonical units, semantic normalization, structured alignment, reports, issue types, and `ProductionIntegrityError`.
- `src/truelogger/rendering.py`: renderer manifest and page-furniture metadata; formatting remains text-preserving.
- `src/truelogger/pipeline.py`: canonical assembly, automatic renderer synchronization, two integrity gates, report persistence, and build failure contract.
- `src/truelogger/models.py`: stable source identity on structured blocks where required.
- `app.py`: finalized-hash state, invalidation, summary, review actions, error rendering, and report download.
- `tests/test_text_qa.py`: normalization and structured difference behavior.
- `tests/test_pipeline.py` and/or a focused production-integrity test module: synchronization, domain error, reports, and production regression coverage.

## Required Tests

Automated coverage will verify:

1. Exact approved text passes.
2. Whitespace-only changes pass.
3. Line wrapping passes.
4. Unicode normalization passes.
5. Page numbers do not trigger failure.
6. TOC content does not trigger failure.
7. Running headers do not trigger failure.
8. Missing paragraphs fail.
9. Duplicate paragraphs fail.
10. Unexpected paragraphs fail.
11. Approved spelling corrections pass.
12. Raw OCR differences are irrelevant when renderer input uses approved text.
13. Stale renderer input is automatically resynchronized.
14. Hindi Unicode passes.
15. English passes.
16. Mixed Hindi/English passes.
17. Modified content and changed order are classified correctly.
18. The UI-facing exception is structured and its report is persisted before raising.
19. The supplied production book passes integrity QA and generates its final PDF.

Tests follow red-green-refactor. The full existing suite must remain green.

## Completion Criteria

The change is complete only when:

- the supplied production book passes both integrity gates and generates the final PDF;
- no approved body text is missing, duplicated, inserted, modified, or reordered;
- the QA report explains every genuine failure by chapter and unit;
- formatting-only PDF differences do not block production;
- stale renderer state is resynchronized or surfaced as a structured conflict;
- the normal UI never exposes the generic integrity traceback;
- all existing and new automated tests pass.
